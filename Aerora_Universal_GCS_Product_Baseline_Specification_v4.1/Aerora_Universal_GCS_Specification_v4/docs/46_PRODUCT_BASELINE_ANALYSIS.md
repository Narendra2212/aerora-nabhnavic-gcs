# 46 — Aerora Hexacopter Product Baseline Analysis

## Purpose

This document records what is actually observable in the uploaded engineering artifacts. It separates confirmed evidence from user-provided product intent and from unresolved engineering assumptions.

## Artifacts analyzed

1. `flight controller pcb(5).kicad_sch` — KiCad schematic.
2. `flight controller pcb(1).kicad_pcb` — KiCad PCB.
3. `motor_test_1__CURRENT.slx` — Simulink model.

## 1. PCB/schematic observations

### Main flight controller

The schematic contains an `STM32H743VITx` as the primary flight-controller MCU.

A second `STM32G071CBTx` is present and is associated with a dedicated watchdog/security/reset interface. The schematic exposes `WATCHDOG_CMD_RX`, `WATCHDOG_CMD_TX`, `WATCHDOG_HEARTBEAT`, `WATCHDOG_NRST`, `WATCHDOG_SWCLK_BOOT0`, `WATCHDOG_SWDIO`, `WATCHDOG_3V3`, and watchdog test points.

### Navigation and sensing

Observed components/interfaces include:
- `ICM-42688-P`
- `ICM-20948`
- two `BMP390L` references
- GPS interface
- companion I/O
- RC receiver interface
- CAN expansion
- microSD
- USB-C

This supports an architecture with redundant/independent sensing paths and dedicated logging/expansion interfaces. Exact sensor-fusion authority and redundancy behavior must be defined by the firmware, not inferred from component presence alone.

### Communications

The schematic contains an `E22-900M22S` module. Its schematic description identifies it as an SX1262 868/915 MHz SPI LoRa module. The design exposes LoRa control nets including `LORA_NSS`, `LORA_TXEN`, and module SPI/status nets.

The schematic also contains `RC_RECEIVER` and companion UART interfaces. The Simulink model separately contains three communications inputs/paths: LoRa, FHSS24 and RF433. The current evidence therefore supports a multi-link architecture, but the exact physical implementation of FHSS24/RF433 must be confirmed separately before being called onboard hardware.

### Vehicle/expansion interfaces

Observed interfaces include:
- six motor signal labels `M1_SIG` through `M6_SIG`
- `MOTOR_BUS`
- `GPS_UART7_RX/TX`
- `COMPANION_UART8_RX/TX`
- `RC_UART5_RX/TX`
- CAN expansion
- USB-C
- microSD
- buzzer
- arm switch
- payload power

### Power

Two schematic connectors are explicitly labelled `Theterd & Battery power input` (`J1` and `J10`). `VIN_RAW` and multiple regulated rails are present. The schematic also contains fuses, current/voltage monitoring using `INA226`, switching regulators and 1.8 V/3.3 V/5 V-related regulation.

The product requirement is now defined as **two operating configurations**:

1. **Tethered painting:** ground supplies **480 V DC** through the tether power cable; an onboard DC-DC conversion stage converts the input to the aircraft 48 V power domain; paint is supplied from the ground through the tether paint hose; the onboard paint tank is detached.
2. **Battery painting:** the onboard battery powers the aircraft; an onboard paint tank is attached; this configuration is intended for complex/remote areas where tether operation is unsuitable.

The uploaded schematic alone does not prove the final **480 V DC-to-48 V DC** converter topology, converter rating, protection/isolation, source arbitration/ORing, tether-loss detection or transition behavior. These remain controlled engineering items. This specification does **not** currently require or claim seamless automatic in-flight switching between the two physical configurations.

### Security/identity hardware

An `ATECC608A-MAHDA` secure element is present. This is an important architectural opportunity for device identity, key storage and secure boot/update-related functions, subject to firmware implementation and provisioning design.

### PCB characteristics

The uploaded PCB is:
- KiCad PCB format version `20260206`
- generated by KiCad 10.0
- 1.6 mm nominal board thickness
- six copper layers: F.Cu, In1.Cu, In2.Cu, In3.Cu, In4.Cu, B.Cu
- approximately 80 mm × 80 mm from the Edge.Cuts geometry
- approximately 157 footprints, 695 pads and more than 2,000 routed segments in the current file

These counts are descriptive of the uploaded revision, not production-quality claims.

## 2. Simulink/firmware observations

The uploaded model is `motor_test` and was saved in MATLAB/Simulink R2026a Update 5.

The model is configured for:
- STM32H7xx Based (Single-core)
- device `STM32H743VITx`
- Embedded Coder/ERT (`ert.tlc`)
- C++ class generation enabled
- code-generation model mappings including `motor_test_c` and `motor_test_cpp`
- periodic function mappings including `Step`, `Step0`, `Step1`, `Step2`
- multiple sample times including observed 0.1 s, 0.01 s, 0.002 s and 0.02 s paths; the model documentation identifies 0.1 s as the current base rate for particular control logic. Exact task timing must be confirmed from the generated scheduling configuration before use as a flight-control timing specification.

### Manual / semi-autonomous / autonomous authority

The model contains explicit authority states:
- MANUAL sentinel = `100`
- AUTO_COVERAGE sentinel = `101`
- SEMI_AUTO_SUPERVISED sentinel = `102`

The observed logic makes manual mode structurally dominant when selected. Semi-auto requires an explicit pilot confirmation input before following the autonomy proposal. Autonomy proposals can be rejected and routed to a safe/default mode.

The current model comments identify the safe/default mode as code `1` and explicitly flag the choice as requiring confirmation against the actual flight-mode mapping. This must remain an open design item rather than being treated as a final operational safety decision.

### Communications arbitration

The model contains `Comms_Arbitration` with inputs for:
- LoRa
- FHSS24
- RF433

The current documented priority is:
1. LoRa — active-link enum `1`
2. FHSS24 — active-link enum `2`
3. RF433 — active-link enum `3`
0. None/all stale

The model uses an all-links-stale condition and arbitrates mode command/confirmation. This is a firmware-side architecture fact in the uploaded model. It must be mirrored in the GCS as a visible link-state model without allowing the GCS to falsely claim a link is authoritative.

### GPU / companion-command path

The model contains a `Mavlink` subsystem with a UART/USART read path and an `Auto_Cmds` output. A separate autonomy/command blend subsystem has future wiring for GPU throttle/roll/pitch commands and GPU-message freshness.

The model comments explicitly describe a manual-dominant assist concept in which GPU assistance is bounded and cannot override manual input. The exact final command authority, freshness timeout, bounds and yaw handling are still engineering decisions.

### Safety mechanisms observed

The model contains:
- arming/disarming logic
- watchdog fault path
- payload emergency stop path
- battery monitoring
- geofence/velocity/acceleration proposal rejection skeletons
- GPS/flow plausibility checking
- parameter CRC validation skeleton
- boot-state skeleton

Several of these are explicitly marked `PLACEHOLDER`, `PENDING`, or `NOT YET INTEGRATED` in the model. They must therefore be treated as **engineering work in progress**, not as verified safety features.

### Painting/payload architecture observed

The model contains a `Payload_Interface`, `Painting_System`, `Payload_Actuator_Drivers`, payload emergency stop and reaction-compensation outputs.

The model includes structural placeholders for:
- gimbal pan/tilt
- spray on/off
- spray rate
- pump PWM
- payload power/safety interlocks
- reaction-force compensation

The model itself states that several actuator ranges, PWM mappings, GPIO assignments and compensation values are placeholders pending real actuator datasheets, hardware pin mapping and reaction-force testing.

## 3. GCS implications

The GCS must expose, at minimum:
- active control authority
- selected communications link
- link freshness/quality
- GPU/companion connection and message freshness
- manual/semi-auto/auto state
- proposal rejection state
- safe/default state
- arming state
- watchdog state
- battery/power source state
- sensor health
- payload safety state
- mission state
- firmware/configuration versions

The GCS must not manufacture these states independently. Where possible it shall display authoritative vehicle-provided state plus clearly distinguish GCS-local observations.

## 4. Important unresolved items

The uploaded artifacts are sufficient to define the architecture direction, but not to close these engineering questions:

- exact tether 480 V DC current limits, protection requirements and allowable operating envelope
- onboard 480 V-to-48 V converter topology, isolation, efficiency, protection and thermal limits
- battery voltage/current limits and energy budget
- physical tether connector/cable/grounding architecture
- source arbitration/ORing/failover circuitry if future hybrid operation is required
- tether-loss detection and response
- exact LoRa configuration and legal operating parameters
- exact FHSS24/RF433 hardware and protocol
- exact RC receiver type
- exact MAVLink message set used between GPU and FC
- exact GPU hardware/model
- exact onboard AI responsibilities
- exact FC task rates and worst-case execution time
- final sensor-fusion algorithm
- final watchdog timeout and reset/latch behavior
- final boot/arming/NPNT state machine
- final geofence data source and policy
- final emergency recovery behavior
- exact payload actuator interfaces
- exact paint pump/nozzle/gimbal hardware
- final power budgets
- final airframe mass/MTOW/payload figures
- final DGCA certification configuration

These become controlled requirements/design tasks rather than assumptions.

## 5. Engineering conclusion

The evidence supports a **distributed intelligent UAV architecture** in which the GCS is one component of a larger system:

`Operator -> GCS -> communications -> FC/vehicle` 

and, in autonomous operations:

`Sensors/mission -> onboard GPU/companion -> MAVLink -> FC -> actuators`

with local safety functions in the FC and payload systems.

The GCS specification must therefore be designed around **authority, redundancy, observability, degraded operation and traceability**, not simply around map/waypoint functionality.
